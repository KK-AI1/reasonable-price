# SPEC.md — 機能と計算の仕様（案）

> **状態：案（2026-10-05 作成）。** 数値の多くは「初期値」で、現地テストで調整する前提です。
> `【要確認】` の付いた項目は、出典の原文で確かめるか、オーナーの判断が必要です。

計算はすべて `src/lib/` の純粋関数で行い、調整しうる数値は JSON 設定に置きます（CLAUDE.md のルール）。
金額は現地通貨（バーツ）の整数で扱います。

---

## 1. 全体の考え方

| 区分 | 例 | 出し方 |
| --- | --- | --- |
| 規制価格 | メータータクシー | 公式料金表から計算（§2） |
| 交渉価格 | 市場の土産物、トゥクトゥク | データから「幅」で推定（§3） |
| 交渉しない | 屋台の食べ物、値札のある店、モール | 「ここは交渉しない場所です」と表示（§3.5） |

交渉コーチ（§4）は、§3 の適正価格の幅を入力にして「次に言う金額」を計算します。
AI は §4 の結果を説明する文章だけを作り、金額は作りません。

## 2. 規制価格：バンコクのメータータクシー

### 2.1 公式料金（2023年1月13日施行）

出典：運輸省告示（2022年／仏暦2565年）。2023年1月13日から適用。

| 区間 | 料金 |
| --- | --- |
| 最初の 1 km | 35 バーツ（一般車）／40 バーツ（大型車）【要確認：車種の区分】 |
| 1〜10 km | 6.50 バーツ／km |
| 10〜20 km | 7.00 バーツ／km |
| 20〜40 km | 8.00 バーツ／km |
| 40〜60 km | 8.50 バーツ／km |
| 60〜80 km | 9.00 バーツ／km |
| 80 km 超 | 10.50 バーツ／km |
| 渋滞・時速 6 km 以下 | 3.00 バーツ／分 |
| 配車センター・アプリ経由の呼び出し | +20 バーツ |
| 空港（スワンナプーム・ドンムアン）の乗り場から乗る | +50 バーツ（メーターに表示されない） |
| 高速道路の料金 | 乗客が実費で払う |

`【要確認】` 大型車の 1 km 以降の料金が一般車と同じかどうかは、告示の原文で確認できていません。
データでは `verified: false` にしておきます。

### 2.2 計算式

```
メーター額 = 初乗り
           + Σ（各区間を走った km × その区間の単価）
           + 渋滞の分数 × 3.00
適正額     = round(メーター額) + 呼び出し料金（該当時）+ 空港料金（該当時）+ 高速料金（入力時）
```

- メーターは実際には細かい単位で上がります。アプリでは**1 バーツ単位に四捨五入**し、「目安」と表示します。
- 渋滞の分数は利用者には分かりにくいため、入力は「渋滞：なし／普通／ひどい」の3択にします。
  1 km あたりの分数に換算し、初期値は 0 / 1 / 3 分です（設定 JSON に置く）【要確認】。
- 距離は、乗る前に利用者が入力するか、端末内で直線距離 × 迂回係数（初期値 1.3）から出します。
  位置情報は端末の外に送りません。

### 2.3 判定（運賃チェック）

運転手の言い値 `ask` が分かったときだけ判定します。比率は `r = ask / 適正額` です。

| 条件 | 判定 | 文言の例 |
| --- | --- | --- |
| r ≤ 1.15 | 妥当 | 「メーター額の目安どおりです」 |
| 1.15 < r ≤ 1.5 | やや高い | 「やや高めです。メーターをお願いしましょう」 |
| r > 1.5 | 高すぎる | 「メーターを使うタクシーを選びましょう」 |

しきい値は設定 JSON に置きます。言い値の固定運賃は違法になりうるため、判定に関わらず「メーターを使ってください」のタイ語フレーズを常に表示します。

## 3. 交渉価格：市場の品目

### 3.1 情報源の種類

適正価格は「売り手も買い手も納得できる額」です。売り手の原価と、地元の相場と、旅行者が実際に払った額の3つから決めます。
旅行者は高めの言い値を出されやすいので、言い値は適正価格の計算に使わず、言い値の予測にだけ使います。

| 種類（`kind`） | 中身 | 使い道 |
| --- | --- | --- |
| `wholesale` | 卸値・工場の値段（1つあたりに換算） | 下限の根拠（売り手の利益を残す） |
| `local` | タイ国内の小売価格（Shopee・Lazada などの通販、地元向けの店頭、タイ語の書き込み） | 目安の中心 |
| `tourist-paid` | 旅行者が交渉して実際に払った額（日本人に限らず世界中の書き込み） | 上限の根拠 |
| `tourist-asked` | 旅行者が最初に言われた額 | 言い値の予測だけ（§4.5） |

### 3.2 データの持ち方（`src/data/items/bangkok-items.json`）

品目ごとに、集めた価格の**観測値**を出典つきで持ちます。値段は1つあたりのバーツに換算して入れ、原文も残します。

```json
{
  "id": "elephant-pants",
  "name": "象柄のパンツ",
  "unit": "1枚",
  "keywords": ["タイパンツ", "กางเกงช้าง"],
  "negotiable": true,
  "observations": [
    {
      "kind": "wholesale",
      "price": 60,
      "venue": "wholesale",
      "quote": "ยกโหล 720 บาท",
      "source": "記事・通販ページの名前",
      "sourceUrl": "https://...",
      "publishedAt": "2025-06",
      "checkedAt": "2026-10-05",
      "verified": false
    }
  ]
}
```

### 3.3 適正価格の幅

基準の売り場（一般の市場）での1つあたりの値を、次のように出します。中央値と分位点を使うのは、件数が少なく外れ値が多いためです。

```
W = 卸値の中央値、L = 地元の小売価格の中央値、T = 旅行者が払った額の値

目安（target）
  L があれば L
  なければ T の中央値
  どちらもなければ W × 標準の小売倍率（初期値 2.0）

下限（low：これより下は売り手が損をしかねない）
  L と T をまとめた値の 25% 点（どちらもなければ target × 0.8）
  W があれば、W × (1 + 最低利益率 0.3) より下にはしない

上限（limit：ここまでなら買ってよい）
  T があれば、T の 75% 点と target × 1.15 の大きい方
  なければ target × 1.3

low ≤ target ≤ limit になるように揃える
```

- 今いる売り場の係数（§3.6）を3つの値に掛けます。
- 倍率・利益率などは `cities/bangkok.json` の `price` に置き、現地テストで調整します【要確認】。
- **データの量の表示**
  - 「卸値・地元・旅行者」のうち2種類以上があり、合計4件以上：通常の表示
  - それ以外で合計2件以上：「データが少ない目安です」と表示
  - それ未満：「データ不足」と表示
- 観測値のうち1件でも `verified: false` があれば「未確認」と表示します。

### 3.4 数量

**現在は、まとめ買いの値引きを適用しません**（設定 `quantityTiers` は 1.0 のみ）。値引きの根拠を現地で確認できるまで、合計は「単価 × 数量」とし、画面にもそう表示します。下の表は、根拠が確認できたときに使う段階表の例です。


まとめ買いの値引きは段階表にします（設定 JSON）。

| 数量 | 1つあたりの係数（初期値） |
| --- | --- |
| 1 | 1.00 |
| 2〜4 | 0.90 |
| 5 以上 | 0.80 |

`合計の幅 = 1つあたりの幅 × 係数 × 数量`

### 3.5 判定（価格チェック）

比率は `r = 提示額 / 目安（中央）` です。

| 条件 | 判定 |
| --- | --- |
| 提示額 ≤ P75 相当 | 妥当 |
| P75 相当 < 提示額 ≤ 目安 × 1.8 | やや高い（交渉の余地あり） |
| 提示額 > 目安 × 1.8 | 高すぎる |

### 3.6 売り場と交渉しない場所

売り場ごとに物価の係数を持ちます（初期値。同じ品物を場所ごとに同じやり方で調べて、比率で直す）。

| 売り場 | 係数 | 交渉 |
| --- | --- | --- |
| 卸売りの市場（プラトゥーナム、サンペン、プラチナム） | 0.8 | する |
| 一般の市場・夜市 | 1.0 | する |
| チャトゥチャック市場 | 1.1 | する |
| MBK などモール内の小さな店 | 1.1 | する |
| 観光通り（カオサン、パッポンなど） | 1.3 | する |
| アジアティーク（露店の言い値は街なかの約1.5倍という報告） | 1.5 | する（小さな店のみ） |
| 屋台の食べ物／値札のある店／モール・コンビニ | ― | しない |

交渉しない売り場では価格計算をせず、「ここは交渉しない場所です」カードを出します。
タイティーやドライマンゴーのように定価で売られる品目（`negotiable: false`）も同じカードを出し、データにある小売価格を「参考の定価」として添えます。

### 3.8 商品の相場画面に出す価格（購入記録の価格帯）

画面の主な価格は、計算した目安ではなく、**旅行者の購入記録（`tourist-paid`）そのままの最小〜最大**です。提示価格・卸値・通販価格は混ぜず、「価格の根拠を見る」の中に種類ごとに分けて出します。§3.3 の目安は交渉コーチで使います。

| 状態 | 条件 | 表示 |
| --- | --- | --- |
| 記録あり | 購入記録が2件以上 | 価格帯・件数・購入時期・対象地域 |
| 単一事例 | 購入記録が1件 | 価格と「購入記録は1件だけです」 |
| 古い記録のみ | 時期の分かる記録だけで、すべて `staleAfterDays`（180日）より前 | 価格帯と「今の値段と違う可能性」 |
| 情報不足 | 購入記録が0件 | 価格を出さず「価格情報が不足しています」 |
| 取得失敗 | データを読み込めない | 「読み込めませんでした」と再読み込み。別のデータに切り替えない |

- 市場を選んでいてその市場の記録がないときは、都市全体の記録を「都市全体」と明記して出します。都市全体の記録を特定の市場の値段として出しません。
- 提示額を入れても「高すぎる」などの判定はせず、購入記録の範囲より低い／範囲内／上限より約◯%高い、とだけ示します。
- 品目は「ふつうの土産物」「ノーブランド品」「メーカー品」を別の品目として持ち、価格を混ぜません。偽ブランド品は扱いません。

### 3.7 トゥクトゥク

メーターがないため、交渉価格として扱います。距離からタクシーの適正額（§2）を出し、それに係数を掛けて幅にします。

```
適正の幅 = タクシー適正額 × [1.0, 1.8]   ← 初期値【要確認：現地データで決める】
```

最低額は 60 バーツ（初期値）とします。トゥクトゥクは「観光用の乗り物」という面があるため、タクシーより高くて当然という前提です。

## 4. 交渉コーチ

### 4.1 使う数字（全員共通）

| 名前 | 中身 | 意味 |
| --- | --- | --- |
| `target`（目標価格） | 目安（P50） | 双方が納得できる価格 |
| `limit`（上限） | P75 | ここまでなら買ってよい |
| `floor`（下限） | P25 × 0.9 | これより下は言わない（失礼になるため） |

CLAUDE.md の原則3・4により、`target`・`limit`・`floor` は誰に対しても同じです。

### 4.2 最初に言う金額

交渉の金額は、双方の最初の言い値の**ほぼ中間**に落ち着きやすいことが知られています（split-the-difference）。
そこで、売り手の最初の言い値 `ask` との中間が `target` になるように、最初の金額を決めます。

```
最初の金額 = clamp( 2 × target − ask , floor , target )
```

- `ask` が `target` 以下：交渉不要。「納得の価格です。買いましょう」
- 最初の金額は、切りのいい数字（初期値は 10 バーツ単位）に切り上げます。下限を下回らないようにするためです。

例：目安 200、P25 160、言い値 400 の場合、`2×200−400 = 0`。下限 `160×0.9=144` で止まり、10 バーツ単位に切り上げて **150 バーツ**から始めます。

### 4.3 次に言う金額（売り手が下げてきたとき）

**譲る幅を毎回小さくし、相手が譲った分の半分だけ譲る**ようにします。交渉の研究で一般的な「譲歩を小さくしていく」進め方です。

```
相手の譲歩     = 前回の相手の額 − 今回の相手の額
こちらの次の額 = min( 前回のこちらの額 + 相手の譲歩 × 0.5 , target )
```

- 0.5（譲歩の比率）は設定 JSON に置きます。
- こちらの額は `target` を超えません。超えそうなときは `target` を最終提示額として示します。

### 4.4 判断（買う・立ち去る）

| 条件 | 表示（判定色） |
| --- | --- |
| 相手の額 ≤ target | 「納得の価格です。買いましょう」（妥当） |
| target < 相手の額 ≤ limit で、相手がこれ以上下げない | 「この額なら買って大丈夫です」（妥当） |
| 相手の額 > limit で、2回続けて相手が下げない | 「笑顔でお礼を言って立ち去りましょう」（やや高い） |

立ち去ると呼び止められて値下げされることも多いため、その場合は §4.3 から続けられるようにします。

### 4.5 提示額の予測（個別化してよい部分）

売り手の最初の言い値を予測し、「このくらい言われるかもしれません」と事前に伝えます。

```
予測される言い値 = target × 上乗せ係数 × 見え方の係数
```

- 上乗せ係数は、`tourist-asked` の中央値 ÷ 目安 から出します。データがなければ初期値 2.0（観光地の市場では「言い値の半分前後で決まる」という一般的な目安から）【要確認】
- 見え方の係数（例：タイ語を少し話す 0.9、グループ 1.0、1人 1.0）は**予測にだけ**使い、`target`・`limit`・`floor` には使いません。
  言語によって最初の言い値が変わることは、フィールド実験でも報告されています。

## 5. 円換算

`円 = round(バーツ × レート ÷ 10) × 10`（10円単位）。

- アプリを開くたびに、最新のレートを無料の API（Frankfurter：欧州中央銀行の参考レート、APIキー不要）から取得します。
- 取得したレートは端末に保存します。オフラインや取得に失敗したときは、保存済みのレートか、アプリに同梱した予備の値（`cities/bangkok.json`）のうち日付が新しい方を使います。
- 画面には「1バーツ＝◯円（YYYY-MM-DD のレート）」と表示します。最新でないときは「保存済みの値」と添えます。
- レートは円換算の表示にだけ使い、適正額や判定の計算には使いません。
- API に送るのは通貨の種類だけで、位置情報などの利用者の情報は送りません。

## 6. 品目の調べ方と、調べた結果の保存（費用を抑える仕組み）

品目の価格は「1度調べたら保存し、同じ品目は2度調べない」を原則にします。
調べるたびに検索 API や AI の料金がかかるためです。

### 6.1 3段階の置き場所

| 段階 | 置き場所 | 費用 | オフライン |
| --- | --- | --- | --- |
| 1 | アプリに同梱するデータ（`bangkok-items.json`）。開発側がまとめて調べ、確認してから入れる | 0円 | 使える |
| 2 | 共有の保存場所（サーバー）。誰かが1度調べた品目を、全員で使い回す | ほぼ0円（無料枠） | 前回分は端末に保存 |
| 3 | 段階1・2にない品目だけ、その場で調べて段階2に保存する | 1品目につき1回だけ | 使えない |

- 「何を買いますか？」の検索は、まず段階1（端末内）を探します。これは費用 0 円です。
- 段階2・3は、サーバー関数（Cloudflare Workers の無料枠など）と保存場所（Cloudflare D1 などの無料枠）を使う予定です。作るにはオーナーのアカウントが必要です【要確認】。
- 段階3の調べ方：検索 API でページを探し、AI にページ内の「値段の原文」だけを抜き出させます。抜き出した値段が原文に本当にあるかを関数で確かめてから、§3.3 の式で幅を出します。AI に値段を決めさせることはしません。
- 1日に調べる品目数に上限を設け、費用が上限を超えないようにします。
- 保存した結果には調べた日付を付け、古くなったもの（初期値 180 日）は「情報が古い」と表示します。調べ直すのは開発側が判断したときだけにします。
- 送るのは品目名だけです。位置情報などの利用者の情報は送りません。

### 6.2 段階1の調べ方（開発側の手順）

1. 卸値：卸売りの市場・工場・まとめ売り（「ราคาส่ง」「ยกโหล」など）の値段を、1つあたりに換算する
2. 地元の小売：タイ国内の通販（Shopee・Lazada）や、タイ語の書き込み（Pantip など）の値段
3. 旅行者：Tripadvisor・Reddit・旅行ブログなど、世界中の旅行者が書いた「実際に払った額」と「最初に言われた額」
4. どれも出典の名前・URL・書かれた時期・原文を記録し、`verified: false` で入れる。現地やオーナーの確認が済んだら `true` にする
